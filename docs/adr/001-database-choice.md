# ADR-001: Выбор PostgreSQL в качестве СУБД

**Дата**: 16 октября 2025
**Статус**: Принято
**Авторы**: Development Team

## Контекст

В спринте S1 необходимо реализовать персистентное хранение истории диалогов пользователей с Telegram-ботом. Текущая реализация использует in-memory хранилище (`dict`), которое теряет данные при перезапуске.

## Рассматриваемые варианты

### 1. SQLite
**Плюсы:**
- Не требует дополнительной инфраструктуры (файловая БД)
- Простая настройка (встроенный aiosqlite)
- Нулевые операционные затраты
- Достаточно для малых и средних нагрузок

**Минусы:**
- Ограниченная конкурентность (один writer)
- Сложности при масштабировании
- Нет встроенной репликации
- Проблемы с concurrent writes

### 2. PostgreSQL
**Плюсы:**
- Production-ready решение
- Отличная конкурентность (MVCC)
- Богатая экосистема инструментов
- Встроенная поддержка репликации и резервного копирования
- Продвинутые типы данных и индексы
- Готовность к масштабированию

**Минусы:**
- Требует отдельный сервис (Docker контейнер)
- Больше операционных затрат
- Сложнее в настройке для разработки

### 3. MySQL/MariaDB
**Плюсы:**
- Популярность и большое комьюнити
- Хорошая производительность

**Минусы:**
- Меньшая поддержка сложных типов данных
- Менее строгие транзакции по умолчанию
- Уступает PostgreSQL по возможностям

## Решение

**Выбран PostgreSQL 17**

## Обоснование

1. **Production-ready с самого начала**: Даже для MVP выбираем технологию, которая не потребует миграции в будущем

2. **Конкурентность**: PostgreSQL отлично справляется с множественными одновременными подключениями, что важно для Telegram-бота с множеством пользователей

3. **Экосистема**:
   - Отличная поддержка в SQLAlchemy
   - Alembic для миграций
   - asyncpg для высокопроизводительной работы
   - PgAdmin, pgcli и другие инструменты для администрирования

4. **Типы данных**: PostgreSQL поддерживает TIMESTAMP WITH TIME ZONE, JSON, массивы - что может пригодиться для будущих фич

5. **Репликация и бэкапы**: Встроенные механизмы для production deployment

6. **Docker**: PostgreSQL легко разворачивается в Docker для локальной разработки

7. **Опыт команды**: Стандарт индустрии для Python-проектов

## Последствия

### Положительные
- ✅ Готовность к production без миграции БД
- ✅ Масштабируемость из коробки
- ✅ Надежность и стабильность
- ✅ Богатая экосистема инструментов

### Отрицательные
- ⚠️ Требуется Docker для локальной разработки
- ⚠️ Больше первоначальной настройки
- ⚠️ Дополнительные операционные затраты (память, CPU)

### Риски и митигации
- **Риск**: Сложность настройки для новых разработчиков
  **Митигация**: Docker Compose с одной командой `make db-up`

- **Риск**: Требования к ресурсам на локальной машине
  **Митигация**: Ограничение ресурсов в docker-compose (memory: 256M)

## Альтернативы в будущем

Если потребуется:
- **Горизонтальное масштабирование**: Citus (PostgreSQL extension)
- **Кэширование**: Redis для hot data
- **Аналитика**: TimescaleDB (PostgreSQL extension для time-series)
