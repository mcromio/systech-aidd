# Development Workflow - Technical Debt

> Правила выполнения работ по [tasklist_tech_dept.md](tasklist_tech_dept.md)  
> Для рефакторинга и улучшения качества кода после code review  
> Все соглашения из [conventions.mdc](../.cursor/rules/conventions.mdc) + дополнительные требования к качеству

---

## 🎯 Основной принцип

**Согласуй → Реализуй → Проверь качество → Подтверди → Коммит**

Работа ведется **строго итерациями** по [tasklist_tech_dept.md](tasklist_tech_dept.md).

---

## 📋 Процесс выполнения итерации

### 1️⃣ Начало итерации

**Действия:**
- Прочитать описание итерации из [tasklist_tech_dept.md](tasklist_tech_dept.md)
- Изучить список задач и проблем
- Понять критерий готовности
- Понять какие стандарты качества нужно соблюсти

**Обновить tasklist_tech_dept.md:**
```markdown
| **TechDebt-N** | Описание | 🔄 IN PROGRESS | 🔲 | - |
```

---

### 2️⃣ Согласование решения

**Перед рефакторингом показать пользователю:**

#### Предлагаемое решение
```markdown
## TechDebt-N: Название

### Текущие проблемы:
1. **Проблема 1**
   - Что не так
   - Где находится

### Предлагаемые изменения:

1. **Файл: src/module_name.py**
   - Было: старая структура
   - Станет: новая структура
   - Причина: принцип SOLID/DRY/и т.д.

2. **Новые инструменты:**
   - mypy для type checking
   - Настройка в pyproject.toml

### Ключевые улучшения:
- Устранение дублирования кода (DRY)
- Разделение ответственности (SOLID)
- Добавление type checking
- Повышение покрытия тестами

### Проверка качества:
- [ ] make format
- [ ] make lint
- [ ] make type-check (если применимо)
- [ ] make test (coverage >= XX%)
```

**Спросить:** "Согласовать этот подход к рефакторингу?"

**Ждать подтверждения от пользователя.**

---

### 3️⃣ Реализация

**После согласования:**

1. **Рефакторинг кода** согласно плану

2. **Следовать всем соглашениям:**
   - ✅ [conventions.mdc](../.cursor/rules/conventions.mdc) - базовые правила
   - ✅ [vision.md](vision.md) - архитектурные принципы
   - ✅ Новые требования к качеству (см. ниже)

3. **Отметить выполненные подзадачи** в [tasklist_tech_dept.md](tasklist_tech_dept.md):
```markdown
- [x] Обновить src/module_name.py
- [x] Обновить tests/test_module_name.py
```

---

### 4️⃣ Проверка качества (расширенная)

**Запустить ВСЕ проверки:**

```bash
# 1. Синхронизация зависимостей (если обновлялся pyproject.toml)
uv sync

# 2. Форматирование кода
make format

# 3. Линтер (ruff)
make lint

# 4. Type checking (mypy) - если применимо с TechDebt-2
make type-check

# 5. Тесты с coverage
make test
# Проверить: coverage не упал, все тесты проходят

# 6. Полная проверка
make check
# Должно включать: lint + type-check + test
```

**Дополнительные проверки для tech debt:**

```bash
# Поиск magic numbers
rg "\b\d+\b" src/ --type py | grep -v "test_" | grep -v "__" | head -20
# Должны быть только в Config или с обоснованием

# Поиск дублирования (если >10 строк повторяются)
# Визуальный анализ или инструменты

# Проверка длины методов (должны быть < 40 строк)
# Визуальный анализ критичных файлов
```

**Сообщить результаты пользователю.**

---

```markdown

- [ ] **conventions.mdc**: Методы < 40 строк ✓
- [ ] **vision.md**: SOLID принципы ✓
- [ ] **vision.md**: Композиция работает ✓
- [ ] **workflow_tech_debt.md**: Все проверки качества пройдены ✓
```

**Все чекбоксы должны быть отмечены!**

---

### 6️⃣ Подтверждение

**Показать пользователю:**
- ✅ Список выполненных задач
- ✅ Результаты всех проверок качества
- ✅ Coverage (не должен упасть)
- ✅ Метрики улучшения:
  - Было X строк дублирования → Стало 0
  - Было X magic numbers → Стало Y (в Config)
  - Coverage: было X% → стало Y%

**Спросить:** "TechDebt-N завершена. Подтверждаете?"

**Ждать подтверждения от пользователя.**

---

### 7️⃣ Обновление прогресса

**После подтверждения обновить [tasklist_tech_dept.md](tasklist_tech_dept.md):**

```markdown
| **TechDebt-N** | Описание | ✅ DONE | ✅ | 2025-10-XX |
```

**Отметить все задачи и чекбоксы:**
```markdown
- [x] Все подзадачи отмечены
- [x] Все чекбоксы "✅ Проверка соответствия стандартам" ✓
```

---

### 8️⃣ Коммит

**Создать коммит с префиксом refactor:**

```bash
git add .
git commit -m "refactor(techdebt-N): Краткое описание

- Устранено дублирование в ModuleName
- Добавлен mypy type checking
- Coverage: XX% → YY%
- Tests: все проходят

Refs: #techdebt-N"
```

**Формат commit message для tech debt:**
- `refactor(techdebt-N):` - рефакторинг tech debt
- `test(techdebt-N):` - только тесты
- `docs(techdebt-N):` - обновление документации
- `chore(techdebt-N):` - настройка инструментов (mypy, ruff)

## ✅ Чеклист для code assistant'а (tech debt)

Перед тем как сообщить "TechDebt-N завершена":

### Базовые требования (conventions.mdc)
- [ ] Все задачи из tasklist_tech_dept.md выполнены
- [ ] Type hints везде (обязательны для всех аргументов и возвратов)
- [ ] Docstrings на русском для публичных методов
- [ ] Логирование через logging (не print())
- [ ] DRY принцип соблюден (нет дублирования > 2 раз)
- [ ] Методы не длинные (макс 30-40 строк)
- [ ] Pydantic модели для структур данных

### Качество кода (дополнительно)
- [ ] SOLID принципы соблюдены (SRP, OCP, и т.д.)
- [ ] Magic numbers вынесены в Config
- [ ] Нет хардкода значений
- [ ] Использованы type hints современного Python (list[], dict[] вместо List[], Dict[])
- [ ] Обработка ошибок везде где нужно (try/except)

### Тестирование
- [ ] Тесты написаны и проходят (0 failed)
- [ ] Coverage не упал (или вырос)
- [ ] Новые тесты для рефакторенного кода
- [ ] Integration тесты (если требуется)

### Инструменты качества
- [ ] `make format` выполнен
- [ ] `make lint` без ошибок
- [ ] `make type-check` без ошибок (если применимо)
- [ ] `make test` проходит с нужным coverage
- [ ] `make check` проходит полностью

### Документация
- [ ] Критерий готовности проверен
- [ ] Чекбоксы "✅ Проверка соответствия стандартам" отмечены
- [ ] tasklist_tech_dept.md обновлен
- [ ] Метрики улучшения зафиксированы

### Завершение
- [ ] Коммит создан с префиксом `refactor(techdebt-N):`
- [ ] Запрошено подтверждение у пользователя

## ⚠️ Важные правила (tech debt)

### ❌ НЕ делай без согласования:
- Не рефакторь код до согласования подхода
- Не переходи к следующей итерации без подтверждения
- Не коммить если coverage упал
- Не пропускай проверку качества
- Не пропускай чекбоксы "✅ Проверка соответствия стандартам"

### ✅ ВСЕГДА делай:
- Показывай план рефакторинга ДО реализации
- Объясняй ПОЧЕМУ нужен рефакторинг (SOLID, DRY, и т.д.)
- Жди подтверждения от пользователя
- Запускай ВСЕ проверки качества (format, lint, type-check, test)
- Обновляй tasklist_tech_dept.md после каждой итерации
- Показывай метрики ДО и ПОСЛЕ рефакторинга
- Делай коммит после завершения итерации
- Запрашивай разрешение на переход к следующей итерации

### 🎯 Фокус на качестве (усиленный):
- Каждая итерация = улучшенный код
- Coverage >= 85% (цель)
- 0 failed tests (обязательно)
- Все линтеры проходят без ошибок
- Type checking проходит (с TechDebt-2)
- SOLID принципы соблюдены
- DRY принцип соблюден
- Методы макс 30-40 строк
- Magic numbers → Config
- Нет дублирования кода

## 🎯 Критерии качества для всех итераций

### Код
- ✅ Type hints везде (Python 3.12 стиль)
- ✅ Docstrings на русском
- ✅ Логирование через logging
- ✅ DRY: нет дублирования > 2 раз
- ✅ SOLID: классы с одной ответственностью
- ✅ Методы < 40 строк
- ✅ Magic numbers → Config
- ✅ Pydantic для структур данных

### Тестирование
- ✅ Coverage >= 85% (целевой)
- ✅ 0 failed tests
- ✅ Integration tests где нужно
- ✅ Моки для внешних API

### Инструменты
- ✅ ruff format + check
- ✅ mypy (с TechDebt-2)
- ✅ pytest + coverage
- ✅ make check проходит

### Архитектура
- ✅ 1 класс = 1 файл = 1 ответственность
- ✅ Явная передача зависимостей
- ✅ Композиция > наследование
- ✅ Async/await везде
